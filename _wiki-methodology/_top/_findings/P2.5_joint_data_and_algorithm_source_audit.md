# Codex+Claude Workflow联合审查：数据完整性确认无遗漏，算法源头盘点，registry漂移修正

## Local Case

用户要求：开workflow跟Codex一起检查数据情况，联网核实算法源头是否有文档，确认Volve/F3/Penobscot是否下载完整，归档进六合一。派了两路独立审查：Codex(secretary_web:28窗口，直连Databricks远端字节级比对)+Claude Workflow(8个并行子智能体，网络搜索交叉验证)。

## Class Pattern

同一个"数据完整性"问题用两条独立证据链交叉验证(远端API直连字节比对 vs 网络搜索社区文档交叉核实)，结论一致时置信度更高；且验证过程本身发现了此前文档的"漂移"(registry文字描述与实测不符，但不是数据缺失)——**完整性核查不仅要验证"东西在不在"，也要顺手验证"描述东西的文字准不准"**。

## Evidence

- Codex审查报告(直连Databricks官方卷做字节级比对，权威性最高)：`_wiki-methodology/_top/_external_reviews/codex_data_algorithm_audit_20260713.md`
- Claude Workflow 8路并行结果(数据2路+6赛道算法各1路)：已整合进本finding与`_entities/volve-dataset.md`

## Impact

**数据完整性：两路独立核实结论一致——完整，无遗漏。**
- Volve：14个ZIP与Databricks远端卷逐文件同名同字节数(0差异)，覆盖Equinor官方11个文件夹类别(项目Wiki此前归并成"9大类"是业务口径，不是官方原始类目数，已在_entities文档更正为"11类官方文件夹→9个业务组→14个ZIP")。
- F3(Zenodo 1471548)：8/8文件MD5全部匹配，无遗漏切片包。
- Penobscot(Zenodo 3924682)：5/5文件MD5全部匹配，无遗漏切片包。

**发现并修正4处registry/文档漂移(不是数据缺失，是描述不准确)：**
1. Volve `size_approx: ~7.7TB` 与实测不符——14个ZIP压缩后实测 **4.566TB**(`du -sh`=4.2T)，`unzip -l`汇总的包内标称未压缩大小约 **5.437TB**，两个数字都不是7.7TB，已在registry和`_entities`文档改为准确数字。
2. "官方9大类"是本项目业务归并口径，Equinor许可证Extract 1原始列出**11个官方文件夹类别**(Seismic细分成ST0202/ST10010/4D/VSP共4个ZIP)，已在`_entities`文档区分清楚"官方11类"vs"我们归并的9个业务组"。
3. F3 registry写"9类标注"不准确，Zenodo页面实际是**9个解释层位分隔出10个地震相区间/类别**，已更正。
4. Penobscot页面文字说7 classes，但本地`dataset-log.txt`记录`num_classes: 8`、HDF5 `label`实读值域0-7——**建模时以数据文件的8个整数标签为准，不要用页面文字的"7"**，这是一个容易踩的坑，已记入`_entities`文档。

**算法源头盘点(6赛道，详见`_entities/algorithm-baselines-6tracks.md`)**：①②③④⑥均有权威公开代码仓库+可运行文档，可直接作为baseline起点；**⑤甜点预测目前只有论文级方法，未确认到作者公开端到端仓库**，且Volve本身没有现成甜点真值——这印证了task_plan里"⑤需要军伟决策代理标签定义"的既有结论，不是新增阻塞，是加固了原判断的证据。

**磁盘状态**：审查时`/mnt/data`为73T总量、64T已用、**5.4T可用、使用率93%**——不建议现在对Volve超大地震ZIP做全量解压，需要先规划训练产物和共享盘余量。

## Prevention Rule (candidate)

跨多个AI(Codex+Claude)重复审查同一批数据完整性时，优先让至少一路走"直连官方API/远端做字节级比对"(最强证据)，另一路走"网络搜索交叉核实社区文档"(补充覆盖面)；两路结论一致才算真正验证过，任一路单独跑都有各自的证据盲区(远端比对可能漏查官方类目定义变化，网络搜索可能被过时的社区二手描述误导)。
