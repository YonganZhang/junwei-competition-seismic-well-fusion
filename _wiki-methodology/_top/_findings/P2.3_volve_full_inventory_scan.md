# Volve数据集完整逐层扫描：修正岩心覆盖结论 + 记录命名陷阱

## Local Case

用户指出之前的核实都是"抽查"（只看顶层目录/部分子目录），可能因为同一口井在不同zip里命名格式不统一（下划线/斜杠/空格、URL编码、无分隔符粘连、多机构前缀重复目录）而漏看真实存在的数据。派任务对全部14个zip做完整`unzip -l`清单+井名正则提取+24口井×数据源覆盖矩阵，产出保存在`_sandbox/volve_data/_full_inventory/`。

## Class Pattern

**"抽查顶层目录"和"全量扫描"得出的结论可能系统性不同**，差异来源不是数据本身缺失，而是命名格式在不同数据源之间不统一（同一物理实体、不同字符串表示）。这是数据资产盘点的一个类层坑：判断"某类数据有没有/有多少"，不能只搜一种命名格式，要先摸清一个数据源内所有命名变体，再统一归并后再下结论。

## Evidence

- `_sandbox/volve_data/_full_inventory/`：14个zip的完整清单文件、`well_zip_matrix.tsv`(24井×数据源覆盖矩阵)、`las_dlis_lis_by_well.tsv`(测井格式覆盖)、`extension_stats_all.txt`

## Impact

**修正P2.1的岩心覆盖结论**：之前认为只有15/9-19 SR一口井有岩心数据（约30-47样本）。全量扫描发现`Well_logs.zip/09.CORE/`下实际有**3个井文件夹**（19A/19BT2/19S&SR），`RMS_model.zip`里19A、19BT2还各自有独立的岩心塞孔渗数值表(`coreplugdata19a`/`coreplugdata19bt2`)。岩心数据源比之前认知的多，具体样本总数待后续精确统计，但"只有1口井"这个说法不准确，需要更正为"发现井群3个井眼（19A/BT2/S&SR）都有岩心资料，其中2个(19A/BT2)在RMS里还有孔渗塞子数值表"。

**核心数据完整性确认**：24口历史钻井在Well_logs/Well_technical_data/LAS测井格式上全覆盖，无遗漏井。地震三个zip内确认含速度模型/道集/震源子波等辅助数据（不只是主体地震体）。

**记录的命名陷阱（供后续查数据时避坑）**：
1. WITSML里路径的`/`被URL编码成`$47$`（如`15_$47$_9-F-15A`实际是`15/9-F-15A`），普通grep搜标准写法会漏
2. RMS模型井目录名完全无分隔符粘连（如`15919a`），跟其他数据源风格不同
3. 同一口井在WITSML里可能被3种不同机构前缀（`NA-NA-`/`Norway-StatoilHydro-`/`Norway-Statoil-`）各建一份并行目录，容易误判成多口井
4. 发现分支合并写法用`&`连接主井眼和侧钻（如`15_9-19 B&BT2`），按单独"BT2"搜索会漏收
5. 未解疑点：WITSML出现`F-15S`编号，不在官方24口井名单（只有F-15/A/B/C/D）里，未强行归并，留作待查

## Prevention Rule (candidate)

盘点跨多个数据源的同一类实体（如"井"）时，先系统提取该实体在每个数据源里的全部命名变体（含编码转换、分隔符差异、机构前缀重复），做归并映射表，再统计覆盖情况；不能只用一种命名格式搜索就下"有/没有/多少"的结论。
