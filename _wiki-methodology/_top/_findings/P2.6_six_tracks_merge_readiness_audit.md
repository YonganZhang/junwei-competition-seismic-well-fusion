# 六赛道worktree合并就绪审计：全部MERGE_READY=NO，核心阻塞是0 commits

## Local Case

①②③④⑤⑥六条赛道baseline pipeline在各自worktree(track-fault/facies/property/lithofacies/sweetspot/reconstruction)里完成并通过独立verify后，派6个Codex worker对各自worktree做只读合并就绪审计（不写文件、不训练、不合并），判定能否安全并入主仓master。

## Class Pattern

"pipeline跑通+指标真实"不等于"可以合并"。多git worktree并行开发时，即使worker在worktree里创建了大量真实产物文件，这些文件默认是**untracked**状态——只要没有实际`git add`+`git commit`，`git merge <branch>`就是合并0个commit、0个文件，即使worktree里文件都在。这是并行worktree协作的一个隐藏坑：产物存在≠可合并。

## Evidence

各赛道完整审计报告见对应tmux pane记录，结论摘要：

| 赛道 | MERGE_READY | 核心阻塞 |
|---|---|---|
| ①断层 | NO | 0 commits；test_fault_real_data.py无条件依赖被gitignore的HDF5无skip guard；README硬编码/usr/bin/python3 |
| ②地震相 | NO | 0 commits；.venv占目录99.96%体积(6.9GB)必须排除；43项untracked文件不能盲目git add -A |
| ③储层物性 | NO | 0 commits；集成测试无条件依赖被忽略的HDF5/guard；build_report.json含3处worktree绝对路径 |
| ④岩相 | NO | 0 commits；.venv 6.5GB(99.98%体积)；README硬编码/mnt/data/.../uv绝对路径；9项测试依赖被排除产物 |
| ⑤甜点 | NO | 0 commits；9个交付文件全部untracked(仅validate-only审计基础设施，无标签无数据) |
| ⑥三维重建 | NO | 0 commits；_tmp/**392MB临时安装文件需排除；HDF5内部仍带旧的过期holdout元数据文案 |

**共性核心阻塞（6/6一致）**：所有track分支HEAD与master同为`60fc639`，ahead/behind=0/0，当前所有交付文件都是untracked。直接`git merge track-X`会合入零内容。

**共性次要问题**：
- 每条赛道都有"轻量单测"vs"依赖真实产物(HDF5/checkpoint)的集成测试"混在一起，干净checkout后集成测试会因缺产物直接失败，需要显式skip guard或拆分测试层级。
- 每条赛道都各自装了独立`.venv`（②③④体积6.5-6.9GB级别，几乎全是PyTorch/CUDA库），6条赛道若都保留独立venv会占用巨大共享盘空间，需要评估是否共享一个环境。
- 部分产物JSON（build_report.json等）里记录了worktree时期的绝对路径，需要改成相对路径或排除。

## Impact

在实际执行`git merge`前，必须先在每个worktree里按各自的INCLUDE清单做**选择性`git add`**（不能`git add -A`，会带入.venv/缓存/HDF5等），提交后才有真正可合并的内容。这是下一步的必要前置动作，不是"锦上添花"的清理。

## Prevention Rule (candidate)

多git worktree并行开发场景，worker完成pipeline后除了独立verify产物真实性，收尾前必须额外确认"是否已实际commit"——git worktree的`git status`/文件存在不能替代`git log`/`ahead-behind`检查。判断"能否合并"要看commit历史而非工作区文件。
